# Архитектура PDPortfolio

Документ фиксирует целевую архитектуру: компонентный фронт, Notion как CMS на базе одной базы «Проекты», статическая сборка.

## 1. Цели

- **Главная** — сетка плиток (обложка, ссылка, краткое описание) без ручной правки разметки при каждом новом проекте.
- **Кейсы** — отдельные страницы с полным контентом, иерархия и маршруты предсказуемы.
- **Смена визуала** — в основном через **дизайн-токены / тему** и layout-компоненты, без переписывания всей вёрстки.
- **Контент** — вы наполняете **Notion**; сайт собирается из экспортируемых данных (CI или ручной запуск синхронизации).
- **Тема** — переключение **светлой** и **тёмной** оформления без смены разметки (токены/режим цвета).
- **Языки** — переключение интерфейса и контента между **русским** и **английским**.

## 2. Технологический стек

**Зафиксировано:** **Nuxt 3** + **Vue 3** (однофайловые компоненты).

- **Вывод в прод:** статическая генерация (**`nuxt generate`** / prerender) — готовый HTML, без обязательного Node на хостинге.
- **Маршруты и SEO:** файловая маршрутизация Nuxt (`pages/`), мета-теги через встроенные средства Nuxt.
- **Notion:** запросы и преобразование контента — на этапе **сборки** или отдельным шагом CI **до** `nuxt generate`; в браузере приложение к Notion не обращается.
- **Тема:** реализация через **`@nuxtjs/color-mode`** (или эквивалент: класс/атрибут на `<html>` + CSS variables для светлого/тёмного набора токенов). Предпочтение пользователя сохранять (например `localStorage`) с учётом `prefers-color-scheme` как стартового значения.
- **Локализация:** **`@nuxtjs/i18n`** (или эквивалент) с локалями **`ru`** и **`en`**; строки UI — в файлах переводов; маршруты и пререндер — согласно стратегии префиксов (например `/ru/…`, `/en/…` или одна локаль без префикса + вторая с префиксом — зафиксировать в конфиге).

## 3. Слои приложения

### 3.1. Модель контента (стабильная схема)

Данные для UI не привязаны к Notion в runtime: на этапе сборки Notion превращается в **JSON / MD(X)** с фиксированными полями.

Пример сущности проекта для UI:

- `slug` — сегмент URL (`/cases/{slug}`)
- `title` — название
- `summary` — текст для плитки
- `cover` — путь или URL обложки (после обработки на сборке)
- `featured` / флаги — показ на главной
- `order` — сортировка
- `status` — только опубликованные попадают в прод

Тело кейса (длинный текст, блоки) — отдельно: страница или фрагмент, сгенерированный из контента страницы записи в Notion.

### 3.2. Компоненты

- **`ProjectCard`** — одна плитка: семантика (`article`, ссылка, заголовок, описание, изображение с `alt`). Внутренняя структура — **контракт**; стили навешиваются на ограниченный набор узлов.
- **`ProjectGrid`** (или аналог) — только **раскладка** главной (сетка, брейкпоинты, отступы). Смена сетки не требует менять разметку карточки.
- Общие **токены** (CSS variables / тема): цвета, типографика, радиусы, отступы. Редизайн — преимущественно здесь.

Правило: не размазывать визуальные классы по страницам; данные приходят пропсами из списка проектов.

### 3.3. Маршрутизация

- Корневые и вложенные пути задаются в Nuxt (`pages/`) с учётом **локали** (см. `@nuxtjs/i18n`): например главная и кейсы доступны на **обоих** языках.
- Условно: `/` (или `/ru`, `/en` — по выбранной схеме) — список проектов с фильтром «на главной», сортировка по полю порядка.
- `/cases/[slug]` — страница кейса по `slug` (с тем же учётом префикса локали, если он используется).

### 3.4. Тема: светлая и тёмная

- Две визуальные темы: **light** и **dark**, переключаемые пользователем (контрол в шапке или аналог).
- Стили опираются на **дизайн-токены** (CSS variables): для каждой темы задаётся набор значений (фон, текст, акценты, границы). Компоненты не дублируются — меняется только набор переменных или класс на корневом элементе.
- Переключение не должно требовать перезагрузки страницы; состояние темы **сохранять** между визитами (и не ломать гидратацию при SSG).

### 3.5. Локализация: русский и английский

- **Инфраструктура:** две локали — **`ru`**, **`en`**; переключатель языка в общем layout рядом с темой (или в одном блоке настроек).
- **UI:** все пользовательские строки интерфейса (кнопки, подписи, навигация, подвал, ошибки) — через **ключи i18n**, без захардкоженного текста в компонентах.
- **Контент из Notion:** заранее определить стратегию: отдельные поля «Название EN / Описание EN» в базе, отдельные страницы на язык, или один язык в CMS и перевод только UI — иначе переключатель языка не изменит тело кейса. Пайплайн сборки должен выгружать **нужные поля/страницы** в структуру данных с учётом локали (например `content/ru/`, `content/en/` или поле `locale` в JSON).
- **SEO:** для каждой локализованной страницы — корректные **`lang`**, **`title`/`description`** на выбранном языке; при необходимости **`hreflang`** между парами `ru`/`en`.

## 4. Notion как CMS: база «Проекты»

Используется **одна database**, каждая строка — проект; **длинный контент** хранится в **теле страницы** этой строки.

### 4.1. Рекомендуемые свойства

| Свойство        | Тип Notion        | Назначение |
|----------------|-------------------|------------|
| Название       | Title             | Имя проекта |
| Slug           | Text              | URL: латиница, без пробелов, уникально |
| Описание (плитка) | Text           | Краткий текст для карточки |
| Обложка        | Files & media или URL | Превью; на сборке — по возможности кэш в репозитории/артефакте |
| На главной     | Checkbox          | Показывать плитку на `/` |
| Порядок        | Number            | Порядок на главной |
| Статус         | Status / Select   | Черновик / Опубликован — в сайт только опубликованные |

Опционально: клиент, год, внешняя ссылка — по мере необходимости.

### 4.2. Правила контента

- **Slug** не менять после публикации (или вводить редиректы).
- Один источник правды — база; дублировать «главную» вручную в Notion не требуется.

## 5. Пайплайн сборки

1. Скрипт (Notion API или экспорт) читает базу: фильтр по статусу, сортировка по **Порядку**.
2. Для каждой строки: свойства → модель для `ProjectCard`; тело страницы → контент страницы кейса.
3. Обработка медиа: presigned URL из Notion при необходимости **скачиваются** на сборке и кладутся в статические ассеты.
4. **Nuxt** собирает статический вывод из Vue-компонентов и данных (`nuxt generate`).

Идеальный режим: **новая строка в Notion + опубликовано** → следующий деплой сам добавляет плитку и страницу без правок кода.

## 6. Деплой: GitHub Pages

Выбранный стек **совместим** с GitHub Pages: `nuxt generate` отдаёт статические HTML/CSS/JS, отдельный сервер Node в проде не требуется.

- **Project Page** (`https://<user>.github.io/<repo>/`): в `nuxt.config` задать **`app.baseURL`** (обычно `/<имя-репозитория>/`), иначе сломаются пути к ассетам и клиентская навигация. Для сайта на корне `username.github.io` base остаётся `'/'`.
- **Динамические маршруты** (`/cases/[slug]` и варианты с префиксом локали): на этапе генерации нужно **явно пререндерить все комбинации** «локаль × slug» из данных Notion (или сгенерированного JSON), чтобы у каждого кейса и языка был свой HTML-файл.
- **404:** у GitHub Pages нет «SPA fallback» как у Netlify/Vercel; несуществующие URL отдают стандартную 404 хостинга. Для полностью сгенерированных маршрутов это ожидаемо.

## 7. SEO

Отдельный сгенерированный HTML на каждый кейс (например `cases/<slug>/index.html` с **уникальным** телом страницы) **не ухудшает** SEO — это нормальная схема SSG: поисковик получает контент в разметке без обязательного выполнения JS.

- Для **каждой** страницы задавать уникальные **`title`** и **`meta description`** (в Nuxt: `useSeoMeta` / `useHead`); при необходимости Open Graph.
- При двух языках — атрибут **`lang`** на `<html>`, по возможности **`hreflang`** для пар `ru`/`en` на эквивалентных страницах.
- Выставить **канонический URL** (`link rel="canonical"`) и **единые правила** URL (например со слэшем или без), чтобы избежать дублей контента на разных адресах.
- Путаница «много `index.html`» не про дубли: у разных маршрутов разные каталоги и **разное** содержимое файла.

## 8. Ограничения и учёт

- Сложные блоки Notion нужно явно маппить в компоненты или упрощённый HTML/MD.
- Живые виджеты Notion в статике не воспроизводятся.
- Лимиты и авторизация API Notion — заложить в документацию деплоя.

## 9. Итог

**Компоненты** (карточка + сетка + тема) отделены от **данных** (схема проекта). **Notion** задаёт контент через **базу с полями** и **страницы строк** для тел кейсов. **Nuxt + Vue** дают SSG, маршрутизацию и компонентную модель под этот пайплайн; выкладка на **GitHub Pages** возможна при настройке **baseURL** и полном **пререндере** маршрутов (**локаль × slug** для кейсов). Пользователь переключает **светлую/тёмную тему** (токены) и **ru/en** (i18n + согласованная схема контента из CMS). **SEO** усиливается уникальными мета-тегами, **`hreflang`** при двух языках и каноникалом. Стилистику можно менять без глобальной переразметки; портфолио наращивается из CMS без ручного добавления плиток в код.
