# DS Workflows

Переносимый набор директив и рабочих процессов для создания, миграции, синхронизации и использования дизайн-системы в проектах.

Эти документы можно подключать к любому проекту как рабочий протокол для агента, дизайнера и разработчика. Они не заменяют конкретную дизайн-систему проекта, а задают порядок её постановки и сопровождения.

## Документы

| Файл | Назначение |
|---|---|
| `directive-01-create-ds-from-scratch.md` | Директива для проекта с нуля: brand brief, контракт, foundation, UI-kit, компоненты, токены в коде |
| `directive-02-migrate-existing-design-to-ds.md` | Директива для проекта с существующими наработками: аудит, нормализация, миграционный контракт, постепенная замена ad-hoc UI |
| `process-playbook.md` | Повторяемые процессы: создать DS, синхронизировать DS с Figma, перенести DS в код, проверить экран, расширить DS компонентом |
| `agent-environment.md` | Развёртывание среды для агента при старте DS-проекта: Figma MCP, структура файлов, доступы, чеклист готовности |

## Базовый принцип

Дизайн-система считается рабочей только если у неё есть три синхронизированных слоя:

1. **Figma**: Variables, Text Styles, Components, актуальные экраны.
2. **DS docs**: `brand-brief.md`, `CONTRACT.md`, `foundation.md`, `components.md`.
3. **Code**: токены и компоненты в формате проекта (`tokens.css`, JSON/TS tokens, Vue/React components и т.д.).

При расхождении между слоями нельзя молча выбирать удобный вариант. Нужно зафиксировать источник правды для конкретного решения, обновить остальные слои и только после этого продолжать UI-работу.

## Канонический порядок перед UI-задачей

1. Открыть нужный Figma frame/node.
2. Прочитать DS docs проекта.
3. Проверить, есть ли нужные токены и компоненты.
4. Если чего-то нет, сначала расширить DS по правилам проекта.
5. Только потом менять экран, код или контент.

## Правило добавления новых правил

Новые правила в DS workflow добавляются только по согласованию, если выполняется хотя бы одно условие:

- ситуация повторилась в двух или более задачах;
- отсутствие правила привело к расхождению Figma, документации и кода;
- правило уменьшает риск ad-hoc решений;
- правило помогает переносить процесс между проектами.

Новое правило должно быть записано в соответствующий документ и, если оно влияет на конкретную DS, продублировано в `CONTRACT.md` проекта.

## Канонические правила Figma MCP

Эти правила считаются обязательными для всех DS-процессов, если задача выполняется через Figma MCP:

- **Сначала текст, потом Figma.** До согласования `brand-brief.md`, `foundation.md`, описаний компонентов или миграционного контракта не выполнять write-вызовы в Figma.
- **Один Figma-файл на продукт.** Wireframes, foundation, UI-kit и финальные экраны живут рядом, если проект явно не требует разделения.
- **Semantic tokens ссылаются на primitive tokens.** В смысловом слое не должно быть прибитых значений, если инструмент поддерживает alias.
- **Компоненты должны быть настоящими Figma components.** Для UI-kit использовать `ComponentNode` / `ComponentSetNode`, а не декоративные frame-заготовки.
- **Text Styles отдельно от цвета.** Типографика хранится в Text Styles, цвет текста привязывается через semantic color variables.
- **Auto Layout везде.** Секции, компоненты и композиции должны выдерживать изменение контента.
- **Мутирующие MCP-вызовы не должны завершаться `throw`.** Проверка результата делается отдельным read-only вызовом, иначе Figma-транзакция может откатить изменения.
- **После write всегда verification pass.** Проверить наличие component sets, text styles, variable bindings и screenshot ключевой секции.
- **Большие DS сканируются индексом.** Для существующей DS читать Variables и верхний уровень Components; не делать рекурсивный обход всего файла.
