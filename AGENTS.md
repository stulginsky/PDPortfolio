# Figma-first portfolio cases

## Источник дизайн-системы

Единым источником документации и разработки дизайн-системы является соседний репозиторий `E:\GitHub\PDPortfolio-DS`.

- Контракты, каталог компонентов, foundation, правила композиции и остальные DS-документы хранятся в `E:\GitHub\PDPortfolio-DS\ds`.
- Figma-контракты, foundation, каталог компонентов, статусы приёмки, skills и directives ведутся в `PDPortfolio-DS`.
- Исполняемые Vue-компоненты и их Storybook stories/sandboxes ведутся в `PDPortfolio`; Storybook импортирует реальные production-компоненты, а не отдельные копии.
- Изменение DS начинается с контракта в `PDPortfolio-DS`, затем реализуется и проверяется в `PDPortfolio`. Отдельная runtime-библиотека в `PDPortfolio-DS` не создаётся без нового архитектурного решения пользователя.
- Локальная папка `PDPortfolio\ds` не используется как источник DS-документации и не должна создаваться.
- Перед разработкой или изменением UI-компонента агент обязан прочитать актуальные документы из `E:\GitHub\PDPortfolio-DS\ds`.
- Для перехода компонента из Figma в production агент обязан применить `E:\GitHub\PDPortfolio-DS\skills\figma-to-production\SKILL.md`; запускающая директива находится в `E:\GitHub\PDPortfolio-DS\directives\directive_figma_to_production.md`.

## Имена компонентов и ассетов

- Каноническое смысловое имя утверждается в Figma после проверки всей группы сопоставимых компонентов или ассетов.
- Код и файловая система используют только механическое преобразование канонического имени: `ArrowNavUp` → `arrow-nav-up.svg`, `DsIconArrowNavUp.vue`, `arrowNavUp`. Самовольная замена смысла запрещена.
- Если имя кажется ошибочным, двусмысленным или несистемным, агент сначала показывает проблему и предлагает схему для всей группы. Переименование начинается только после решения пользователя и сначала выполняется в Figma.
- Переименование завершено только после синхронизации Figma, `E:\GitHub\PDPortfolio-DS\ds\assets.md`, файла ассета, production-кода, stories, документации и всех импортов.
- При несовпадении имён агент обязан остановиться, перечислить обе стороны и запросить каноническое имя; выбирать победителя или создавать алиас без решения пользователя нельзя.
- До экспорта или переименования ассетов прочитать `E:\GitHub\PDPortfolio-DS\ds\naming.md` и проверить реестр `E:\GitHub\PDPortfolio-DS\ds\assets.md`.

Для страницы кейса, реализуемой по переданному Figma-узлу, обязательно использовать skill `figma-exact-case-build`. Figma-узел — визуальная спецификация, а не смысловой референс: до кода составить карту всех дочерних фреймов, сохранить порядок, геометрию, ассеты и иерархию, затем сравнить локальный результат с Figma в совпадающих desktop/mobile viewport до объявления страницы готовой.

Нельзя объединять, переставлять, дублировать или выдумывать контент кейса, слои, фоны, иконки, адаптивное поведение и универсальные обёртки без явного источника в Figma или решения пользователя. Если локальный визуальный capture недоступен, отмечать визуальную проверку как незавершённую, а не делать вывод о готовности по успешному build.

## Текст кейса из Figma

Финальный текст Figma не размещается в `.vue`. Для каждого кейса обязательна цепочка `Figma → content/sources/cases/<case>.json → npm run typograf:apply → content/cases/<case>.json → TypoText`. Если пользователь передал вручную оттипографированный текст, он хранится отдельно в `content/sources/cases/<case>.typograf.txt` с HTML-сущностями (`&nbsp;`, `&mdash;` и т. д.); build декодирует их, но не запускает этот текст через Typograf повторно.

В Vue разрешены только ссылки на сгенерированные строки и служебные шаблоны подстановки. Перед завершением проверить, что все видимые текстовые данные страницы и её case-компонентов поступают из сгенерированного JSON, а составные термины с дефисом (`AI-`, `B2B-`, `B2C-`, `UX-`, `UI-`, `MVP-`) после apply содержат неразрывный дефис.

# Storybook MCP

При работе с UI-компонентами использовать проектный MCP `pdportfolio_storybook`, когда Storybook запущен на `http://127.0.0.1:6006`.

- Перед использованием существующего компонента запросить его фактический API и stories через `docs-list` / `docs-show`; не придумывать props по имени.
- Перед созданием или изменением stories запросить `get-storybook-story-instructions`.
- После изменения компонента или story запускать `test-run` для затронутых stories; исправлять render, interaction и accessibility errors до передачи пользователю.
- Storybook MCP является интерфейсом к исполняемой реализации, но не заменяет Figma и DS-контракты как источники дизайна и поведения.
- Если MCP недоступен, выполнить `npm run build-storybook` и `npm run test-storybook`, явно отметив отсутствие MCP-проверки.

# Figma → код для компонентов дизайн-системы

Для любого изменения UI-компонента из DS выполнять шаги строго по порядку:

1. Взять Component Set из Figma и прочитать все его варианты и свойства.
2. Взять готовые SVG и графические ассеты из Figma, не рисовать им замену в коде.
3. Один раз зафиксировать таблицу состояний и semantic tokens в `ds/components.md`.
4. Внедрить компонент в страницу без локальных догадок, новых визуальных правил или подмены ассетов.

Скриншот применяется только для финальной визуальной сверки. Если Component Set, его графика или названия состояний противоречат друг другу, остановиться и запросить решение до изменения кода.
