# Review & Plan

## Краткий вывод

Проект можно продолжать. Техническая база рабочая: Nuxt/Vue, компонентная структура, контент в `content`, ассеты в `public`, дизайн-токены в CSS, отдельный typograf-пайплайн перед сборкой.

Сейчас проект выглядит как рабочий прототип после активной сборки. Главная задача перед дальнейшей разработкой - стабилизировать базу: git, статическая генерация, контент-пайплайн и минимальные проверки.

## Что уже хорошо

- Стек подходит для портфолио: Nuxt + Vue, возможна статическая генерация.
- `npm run build` проходит успешно.
- Структура проекта читаемая: `app/pages`, `app/components`, `app/types`, `app/utils`, `content`, `public`, `scripts`.
- Карточки главной вынесены в JSON и типизированы.
- Есть дизайн-токены в `app/assets/css/tokens.css`.
- Есть typograf-пайплайн: `typograf:apply`, `typograf:preview`.
- Контент из Notion уже частично присутствует в `content/notion/cases`.

## Главные проблемы

### 1. `npm run generate` падает

Статическая генерация сейчас завершается ошибкой из-за двух ссылок из кейса Chirp:

- `/cases/nested-chirp-ai-check`
- `/cases/nested-chirp-brand`

Ссылки есть в `app/pages/cases/chirp-ai-health-assistant.vue`, но соответствующих Vue-страниц в `app/pages/cases` нет.

При этом markdown-источники для этих страниц уже есть:

- `content/notion/cases/nested-chirp-ai-check.md`
- `content/notion/cases/nested-chirp-brand.md`

Это блокер для деплоя на GitHub Pages/SSG.

### 2. Git-состояние не стабилизировано

`git status --short` показывает весь проект как `untracked`. Значит сейчас нет нормальной зафиксированной базы, от которой можно безопасно продолжать.

Перед активной разработкой нужно:

- проверить `.gitignore`;
- исключить служебные директории и build-артефакты;
- сделать первый осознанный commit.

### 3. Архитектура описывает больше, чем реализовано

В `architecture.md` заложены:

- light/dark theme;
- i18n `ru/en`;
- GitHub Pages `baseURL`;
- полный prerender маршрутов;
- Notion как CMS.

В коде это пока реализовано частично. Это нормально для прототипа, но важно не считать эти пункты готовыми.

### 4. Контент-подход пока смешанный

Дальше Notion не используем как источник контента. Нужно перейти к typed markdown в репозитории и явно отделить новый контент-процесс от старых Notion-артефактов:

- Figma задает концепт и визуальную структуру кейса;
- typed markdown хранит метаданные, текст и ссылки на ассеты;
- DS/Vue-компоненты задают допустимые блоки рендера.

Для масштабирования нужен ограниченный словарь блоков и типизированный рендерер, чтобы markdown не превратился в хаотичный документ.

### 5. SEO пока минимальный

`useSiteHead` сейчас задает в основном `title`. Нужно добавить:

- `description`;
- Open Graph;
- canonical URL;
- `lang`;
- при i18n - `hreflang`.

### 6. Нет базовых quality gates

В `package.json` нет отдельных скриптов:

- `typecheck`;
- `lint`;
- тесты;
- CI-проверка `generate`.

Минимально стоит добавить typecheck и проверку генерации перед деплоем.

### Этап 2. Маршруты и контент

Решение: Notion исключаем из контент-процесса. Источник концепции и визуальной структуры кейса - Figma-макет. Источник текста, метаданных и ссылок на ассеты - typed markdown в репозитории. Повторяемые паттерны из Figma переносим в DS и Vue-компоненты, а `.md` используем как ручную текстовую CMS с ограниченным словарем блоков.

Базовый словарь блоков: `case-hero`, `case-section`, `case-gallery`, `case-metrics`, `case-role`, `case-problem`, `case-process`, `case-result`, `case-next`, `case-media`.

### Медиа-компоненты для кейсов

Сложные схемы и большие интерфейсные экраны должны оставаться читаемыми: в потоке кейса они показываются в заданном макетом масштабе, а по действию пользователя открываются для изучения. Для этого вводим три составных Vue/DS-компонента:

- **`CaseMediaFrame`** (`layout-image-box`) - универсальная фоновая поверхность для изображения в потоке страницы. Отвечает за рамку, отступы, тему и адаптивный размер, но не за само содержимое.
- **`CaseMediaBackdrop`** (`1920-backdrop`) - универсальный полупрозрачный полноэкранный backdrop для режима просмотра. Он отделен от `CaseMediaFrame`, чтобы тему и визуальный слой можно было менять независимо.
- **`CaseImageViewer`** - интерактивный viewer, который собирает backdrop и медиа-слой: открытие/закрытие, увеличение, уменьшение, сброс масштаба и панорамирование. На мобильном - pinch-to-zoom и перетаскивание; на десктопе - колесо, drag, клавиатура и кнопки управления.

Блок **`case-media`** в typed markdown задает ассет, `alt`, вариант поверхности и возможность увеличения; он рендерится через эти компоненты. Он применяется и к одиночным изображениям, и к составным интерфейсным схемам с мелкими экранами и подписями. Для обычной последовательности экранов остается `case-gallery`.

SVG-схемы не переводим в растровый формат: SVG остается отдельным векторным ассетом. `CaseMediaFrame` и `CaseImageViewer` могут показывать его в том же сценарии, если конкретной схеме нужен просмотр в увеличении.

Отдельный интерактивный компонент для схемы создаем только когда ее элементы должны быть кликабельны, раскрывать детали или вести по сценарию. Для задач чтения и исследования достаточно `CaseImageViewer`.

Шаблон `content/templates/case-template.md` уже показывает будущую чистую схему ассетов, но сами файлы под нее еще не перенесены. В браузере путь `/cases/<slug>/hero.png` соответствует файлу `public/cases/<slug>/hero.png`.
