# Директива 02 — собрать дизайн-систему из существующих наработок

Использовать, когда в проекте уже есть макеты, скриншоты, готовый код, UI-фрагменты или брендовые материалы, но нет единой дизайн-системы.

## Цель

Превратить существующий визуальный хаос в управляемую DS без полного переписывания продукта.

Результат директивы:

- аудит текущих решений;
- нормализованные primitive и semantic tokens;
- каталог повторяющихся компонентов;
- миграционный `CONTRACT.md`;
- план перевода legacy UI на DS;
- правило: все новые экраны делаются только через DS.

## 1. Провести аудит

Источники аудита:

- Figma files и выбранные frame/node;
- скриншоты продукта;
- Storybook или компонентная песочница, если есть;
- код компонентов;
- CSS/SCSS/Tailwind classes;
- дизайн-токены, если они уже частично существуют;
- брендбук, презентации, лендинги, маркетинговые страницы.

Что извлекаем:

| Категория | Что искать |
|---|---|
| Цвета | Повторяющиеся фоны, текст, акценты, состояния, ошибки |
| Типографика | Шрифты, размеры, веса, line-height, letter-spacing |
| Отступы | Частые gaps, paddings, section spacing |
| Радиусы | Карточки, кнопки, инпуты, аватары |
| Тени | Elevation, hover, sticky nav |
| Компоненты | Badge, Button, Card, Nav, Form, Modal, Tabs, Filters |
| Состояния | Default, hover, active, focus, disabled, error, loading |

## 2. Нормализовать токены

Сначала собрать фактические значения, затем сгруппировать их.

Пример:

- `#FFFFFF`, `#FAFAF9`, `#F9FAFB` → выбрать один `gray-00` или развести роли;
- `12`, `13`, `14`, `15` px → привести к шкале `xs/sm/base`;
- `7`, `8`, `9` px radius → выбрать `radius/md = 8`;
- несколько похожих акцентов → определить primary, hover, pressed.

После нормализации:

1. записать primitive tokens в `foundation.md`;
2. поверх них создать semantic tokens;
3. отметить legacy values, которые временно остаются.

Нельзя удалять legacy-значение только потому, что оно “некрасивое”. Сначала нужно понять, где оно используется и можно ли заменить его без регрессии.

## 3. Собрать компонентный каталог

Компоненты выделяются из повторяющихся паттернов, а не из одного частного экрана.

Минимальный стартовый набор:

- Badge / Tag;
- Button;
- Icon button;
- Card;
- TopNav / Header;
- Tabs / Segmented control;
- Filter;
- Input;
- Form field;
- Modal / Drawer, если есть в продукте.

Для каждого компонента фиксируются:

- назначение;
- Figma node-id;
- варианты;
- состояния;
- используемые токены;
- где уже используется;
- что осталось legacy.

## 4. Создать миграционный `CONTRACT.md`

В проекте с существующим UI контракт должен различать новое и legacy.

Обязательные разделы:

- что считается источником правды;
- какие экраны уже переведены на DS;
- какие зоны остаются legacy;
- как добавлять новый компонент;
- как заменять legacy компонент;
- какие ad-hoc решения запрещены сразу;
- какие ad-hoc решения разрешены временно и до какого события.

Базовое правило:

> Новый UI делается только через DS. Legacy UI не трогаем без задачи на миграцию, но при касании переводим затронутую часть на токены и компоненты, если это не ломает объём задачи.

## 5. Постепенно заменить ad-hoc UI

Миграция должна идти малыми безопасными шагами:

1. сначала токены;
2. затем базовые компоненты;
3. затем повторяющиеся блоки;
4. затем экраны целиком;
5. затем удаление legacy CSS/variants.

Каждый шаг должен иметь проверку: визуальное соответствие, отсутствие regressions, обновлённые DS docs.

## 6. Новые экраны делать только через DS

После постановки миграционного контракта:

- новый экран не может вводить новый цвет напрямую;
- новый компонент не может жить только внутри экрана;
- новый вариант компонента должен попасть в Figma и `components.md`;
- если нужен новый semantic token, он добавляется в `foundation.md` до использования в коде.

## Definition of Done

Миграция считается запущенной корректно, когда:

- аудит завершён и основные повторяющиеся значения известны;
- `foundation.md` содержит нормализованные tokens;
- `components.md` содержит стартовый каталог компонентов;
- `CONTRACT.md` различает DS и legacy зоны;
- в коде есть первый слой токенов;
- новые UI-задачи могут выполняться без увеличения ad-hoc долга.

## Implementation addendum — scan existing DS

Если директива выполняется как индексация существующей Figma DS, действуют дополнительные технические правила:

- Scan существующей DS по умолчанию read-only.
- Сначала создать `ds/source.md`: источник, ссылка на Components/foundation, локаль, дата, ограничения доступа.
- Для больших Figma DS читать Variables и верхний уровень страницы Components; не делать рекурсивный обход всего файла.
- Не заходить внутрь instances и не разворачивать все комбинации variants.
- Для `ComponentSetNode` фиксировать matrix variants компактной строкой.
- Компоненты без описаний, подозрительные имена, дубликаты и старые версии выносить в self-check.
- Если источник корпоративный, агент не правит исходную DS без отдельного разрешения.
- Если нужного компонента нет в корпоративной DS, сначала искать композицию из существующих компонентов; локальный паттерн фиксировать в `ds/patterns.md`.
- Индекс не считается рабочей DS, пока не создан `CONTRACT.md`.
