# DS Process Playbook

Повторяемые рабочие процессы для создания, синхронизации и использования дизайн-системы.

## Процесс 1 — создать DS

Использовать для нового проекта или после решения формализовать существующий визуальный язык.

1. Собрать brand brief.
2. Создать `CONTRACT.md`.
3. Описать primitive tokens в `foundation.md`.
4. Описать semantic tokens в `foundation.md`.
5. Создать Variables, Text Styles и Effect Styles в Figma.
6. Создать базовые компоненты в UI-kit.
7. Записать компоненты в `components.md`.
8. Зеркалить токены в код.
9. Собрать первый экран только через DS.
10. Проверить, что Figma, DS docs и code совпадают.

Контрольные вопросы:

- Можно ли собрать новый экран без нового ad-hoc hex?
- Есть ли у каждого базового компонента node-id?
- Понятно ли, как добавить новый токен?
- Понятно ли, как добавить новый компонент?

## Процесс 2 — синхронизировать DS с Figma

Использовать, когда Figma изменилась или есть подозрение, что документация устарела.

1. Открыть Figma file и нужный frame/node.
2. Считать Variables, Text Styles, Components и relevant screens.
3. Сравнить с `foundation.md` и `components.md`.
4. Найти расхождения:
   - новый токен есть в Figma, но нет в docs;
   - токен есть в docs, но не используется в Figma;
   - компонент изменился, но node-id/variants не обновлены;
   - screen использует ad-hoc значение.
5. Согласовать источник правды.
6. Обновить Figma или DS docs.
7. Если изменения влияют на продуктовый код, обновить code tokens/components.
8. Зафиксировать итог в задаче или changelog проекта.

Правило:

> Синхронизация завершается не тогда, когда найдено расхождение, а когда обновлены все затронутые слои: Figma, DS docs, code.

## Процесс 3 — перенести DS в код

Использовать после постановки или изменения foundation/components.

1. Прочитать `CONTRACT.md`.
2. Прочитать `foundation.md`.
3. Определить формат токенов проекта: CSS variables, JSON, TS, SCSS, Tailwind config.
4. Создать или обновить token layer.
5. Сопоставить semantic tokens с CSS/API именами.
6. Обновить базовые стили: typography, surfaces, text, borders, focus states.
7. Реализовать или обновить компоненты UI-kit.
8. Проверить отсутствие случайных hex в новых компонентах.
9. Запустить build/test/lint, если они есть в проекте.
10. Визуально сверить ключевые экраны с Figma.

Рекомендуемая структура для web-проекта:

```text
app/assets/css/tokens.css
app/assets/css/base.css
app/components/ui/
content/design-system/
```

Структура может отличаться, но источник правды должен оставаться один.

## Процесс 4 — проверить экран на соответствие DS

Использовать перед завершением UI-задачи или при ревью.

1. Открыть Figma frame экрана.
2. Прочитать DS docs проекта.
3. Проверить цвета:
   - semantic tokens вместо случайных hex;
   - корректные text/surface/border roles;
   - состояния hover/active/focus/disabled.
4. Проверить типографику:
   - Text Styles или кодовые классы DS;
   - line-height и letter-spacing;
   - переносы и длину строк на локалях проекта.
5. Проверить layout:
   - Auto Layout в Figma;
   - стабильные размеры и constraints в коде;
   - responsive states.
6. Проверить компоненты:
   - используются DS-компоненты;
   - новые variants задокументированы;
   - нет локального компонента-дубликата.
7. Проверить доступность:
   - contrast;
   - focus visible;
   - hit area;
   - semantic HTML / aria там, где нужно.
8. Проверить визуально desktop и mobile.

Итог проверки должен быть одним из трёх:

- соответствует DS;
- соответствует DS, но есть согласованные исключения;
- не соответствует DS, нужен список правок.

## Процесс 5 — расширить DS новым компонентом

Использовать, когда для задачи нужен UI-паттерн, которого нет в каталоге.

1. Проверить, нет ли уже подходящего компонента или variant.
2. Если нет, описать назначение нового компонента.
3. Проверить, есть ли нужные semantic tokens.
4. Если токенов нет, сначала расширить `foundation.md`.
5. Создать компонент в Figma UI-kit.
6. Привязать Variables, Text Styles, Effect Styles.
7. Создать variants и states.
8. Записать компонент в `components.md`.
9. Реализовать компонент в коде.
10. Использовать компонент на экране.
11. Проверить Figma ↔ DS docs ↔ code.

Компонент нельзя считать добавленным в DS, если он существует только в Figma или только в коде.

## Процесс 6 — добавить новый токен

Использовать, когда существующих токенов недостаточно.

1. Определить, это primitive или semantic token.
2. Проверить, можно ли решить задачу существующим semantic token.
3. Если нужен новый primitive, объяснить почему текущей шкалы недостаточно.
4. Если нужен semantic, привязать его к primitive.
5. Добавить token в Figma Variables.
6. Добавить token в `foundation.md`.
7. Добавить token в code token layer.
8. Заменить ad-hoc usage на новый token.

Новый token должен иметь роль. Если роль не получается назвать, вероятно это не token, а частное значение.

## Operational addendum — Figma MCP best practices

### Figma write safety

- До write-вызовов согласовать markdown-структуру результата.
- Не завершать мутирующий Figma-вызов через `throw`; это может откатить всю транзакцию.
- После каждого write-вызова делать отдельный read-only verification pass.
- Проверять, что UI-kit узлы имеют type `COMPONENT` / `COMPONENT_SET`, а не `FRAME`.
- Проверять, что Text Styles применены к текстовым узлам.
- Проверять, что fills/strokes привязаны к Variables.
- Получать screenshot ключевой секции/frame.

### Индексация больших DS

- Не читать корень большого Figma-файла целиком.
- Запрашивать ссылку именно на страницу Components или конкретный frame/node.
- Читать Variables и верхний уровень Components.
- Группировать components по смысловым разделам: действия, ввод, контейнеры, навигация, фидбэк, данные, прочее.
- Для ru/ru+en отдельно отмечать поддержку кириллицы шрифтом.

### Расширение UI-kit

- Перед добавлением компонента прочитать текущий `components.md` и проверить дубликаты.
- Если близкий компонент уже есть, расширить его variants вместо создания нового компонента.
- Стартовую variant matrix держать компактной: 2-3 ключевых варианта.
- При Figma MCP добавлять компоненты пакетами по 2-3 на write-вызов.
- Если `Foundation` уже поставлен, новые компоненты размещать в отдельной секции `UI Kit — extended` рядом с ним.
- Использовать существующие Text Styles; новую типографическую шкалу не создавать внутри grow-процесса.
